# Linked catalog protocol

An installed catalog entry can have one linked copy per enrolled device for the
same owner. Linking uses catalog IDs and exact versions. Local screen names play
no role. Existing installs and local screens remain independent until an explicit linked
install activates the catalog entry.

## Negotiation

Use the API origin and the device's bearer credential. Send
`X-Screenpunk-Catalog-Links: 1` on `GET /api/catalog/capabilities` and require
`linkedInstallVersion: "1"` in the response before using this protocol. Ordinary
catalog and authoring versions continue independently. The capability does
not change the owner's backup entitlement or quota. Shared writes also use the
asset-backed upload protocol, negotiated with
`X-Screenpunk-Catalog-Assets: 1` and `assetBackupVersion: "1"`.

## Install and follow

1. Download the selected entry’s current immutable head using its catalog screen ID,
   version ID, source revision ID, and package digest. Verify the package
   before installation using the ordinary catalog restore rules.
2. Stop if the local install fails. After a durable local install, acknowledge
   that exact version with the request below. Acknowledgment associates the
   exact enrollment, library and local screen with the catalog screen. The
   server verifies the package identity against the retained version. A newer
   head can be returned alongside the acknowledged version.
3. Persist the returned `copyID` and `installedVersionID` with the local
   install. Consult the current head returned by the server or by the updates
   route to catch up. Reuse the exact acknowledgment on transport retry when
   its version is retained. Repeating an older acknowledgment cannot rewind the copy.

The first linked install also registers the producing copy when the server can
identify its current enrollment and acknowledged version. It uses the
producer’s recorded identity and revision, with no matching by screen name.

`POST /api/catalog/linked-installs` accepts a JSON body up to 4096 bytes.

```json
{
  "schemaVersion": 1,
  "catalogScreenID": "123e4567-e89b-12d3-a456-426614174001",
  "versionID": "123e4567-e89b-12d3-a456-426614174002",
  "sourceRevisionID": "source-revision",
  "packageDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "libraryID": "local-library",
  "localScreenID": "local-screen",
  "localRevisionID": "installed-local-revision",
  "commitCounter": 1
}
```

`GET /api/catalog/linked-installs/updates?cursor=...` returns
`{schemaVersion:1, subscriptions:[...], nextCursor?}`. For the first page, omit
the cursor. Treat cursors as opaque, and finish each pagination pass before
starting another. Each page contains up to 20 subscriptions. Each item, also
returned by a successful install or acknowledgment, contains `schemaVersion`,
`catalogScreenID`, `copyID`, `libraryID`, `localScreenID`, `localRevisionID`,
`commitCounter`, `installedVersionID`, `installedSourceRevisionID`,
`installedDisplayVersion`, `installedPackageDigest` and `linkedDeviceCount`.
The installed fields identify the copy’s acknowledged immutable version,
including when it differs from the current head. The count includes this device. The optional `current` is an ordinary immutable
`CatalogVersion` for the current head.

Catalog screen, version and copy IDs are lowercase UUIDs generated by the
catalog. Device-local IDs use up to 128 ASCII letters, digits, underscores or
hyphens and begin with a letter or digit.

A follower applies a new head in place to the registered screen only after
checking that the library, screen and local base still match. It uses the
ordinary exact-version download and package verification, then acknowledges
the version after committing it locally. Applying a remote head is a restore
and must not queue a shared publication. An offline follower can catch up from
the latest head without replaying all intervening edits. Recheck the head on a
subsequent pass if a version disappeared or was superseded during download.

## Publish a shared edit

Use the existing resumable asset-backed backup flow. Add an exact `link`
object to the asset begin envelope.

```json
{
  "catalogScreenID": "123e4567-e89b-12d3-a456-426614174001",
  "baseVersionID": "123e4567-e89b-12d3-a456-426614174002"
}
```

The backup belongs to the currently registered local copy. Its predecessor is
the acknowledged local revision and its counter advances from the acknowledged
counter. Keep the originally edited version in `baseVersionID` on retries.
The server compares that version with the shared head before publication. A
successful completion adds an immutable catalog version and advances the
shared head. A legacy producer can continue its ordinary backup flow while its last
acknowledged version matches the shared head. The server checks that base
again at completion.

If a different publication has already advanced the head, begin can return
`conflict` and a pending operation can complete with terminal `failed` and
`error.code: "conflict"`. Preserve the edited bytes locally, and offer to keep
the edit as a separately named independent screen. Retrying against a newly
observed head would discard the compare-and-swap protection.

## Stop following or fork

`DELETE /api/catalog/linked-installs/{catalogScreenID}?copyID={copyID}`
unsubscribes the exact registered copy and can be retried. The response is
`{schemaVersion:1, catalogScreenID, deleted:true}`. The copy ID guards against
a stale unlink affecting a replacement registration. Unsubscribing leaves the
shared catalog and other devices' installations intact.

For an edit scoped to this device only, keep the edited package as a newly
named independent screen with a new local screen identity, and stop following
the linked copy. Explicitly choosing a fork queues its initial catalog publication even when
automatic backups are disabled. Do not
reuse the old linked tuple for independent backups.
