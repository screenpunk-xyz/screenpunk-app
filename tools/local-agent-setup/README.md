# Reviewed Mac pairing bootstrap

`macos/macos.sh` is the current versioned download for `/local/setup/v6/macos.sh`. Published v1, v2, v3, v4 and v5 bytes remain frozen under `releases/v1/`, `releases/v2/`, `releases/v3/`, `releases/v4/` and `releases/v5/` and their original public URLs. It embeds `macos/native.js`, using only macOS shell tools, JavaScript for Automation, Foundation, CoreImage and AppKit. No Python, Node, Xcode, separate computer app, network enrollment listener or external QR encoder is required on the user's Mac. V4 offers a user-approved per-user LaunchAgent so Terminal can close after verified background startup.

The public page contains one Mac command: create a new download file, fetch the versioned script over HTTPS, verify its SHA256, then run it. The page never receives request/reply contents. Its CSP allows only the exact generated script hash and inline style, with no connections, forms, frames or external images. The downloaded source is directly reviewable. Every published version is frozen; later changes require a new URL/version and checksum. The Cloud route owner wires the generated exports and security/cache headers.

Generate/check reproducibility:

```
node tools/local-agent-setup/generate.mjs
node tools/local-agent-setup/generate.mjs --check
/bin/sh -n tools/local-agent-setup/macos/macos.sh
```

Run `node --test tools/local-agent-setup/tests.mjs` on macOS with graphics access. CoreImage context creation is denied by the Codex exec sandbox; the synthetic-only suite may require approved execution outside that sandbox. Every setup execution transforms fixed production constants into temporary fake HOME/PATH/config paths and stub Codex, sudo, sshd, host keys, listener, computer name and account commands. It never runs actual setup, Codex login/inference, Remote Login changes, keychain access or host-key generation. Pure parser tests also run on Node without macOS. `node tools/local-agent-setup/native-display-test.mjs` explicitly checks the native fallback and QR accessory windows with synthetic two-second expiry dialogs on a logged-in graphical Mac. Fixture ownership/removal receipts live under the stable evidence/mac-setup scratch root. Both test commands accept `SCREENPUNK_SETUP_TEST_ROOT` (evidence directory; fixtures and receipts are children) and optional `SCREENPUNK_SETUP_TEST_OWNER`; CI can set these to its own exact task root/owner. No other flags are required. Do not run `macos.sh` directly during development.

The script supports Apple Silicon macOS 13+ and the pinned bundled Codex version/hash. An unknown installation is never installed, selected, downgraded or repaired automatically. It uses a dedicated private Codex home without exporting global credentials. Existing tokens require exact private-file provenance. The bearer never reaches command arguments, stdout, clipboard, a URL or a network QR encoder. Only a public request is selected through the native file chooser; the private QR/reply file stays in a private local session, expires after five minutes, and is cleared on dismissal. Oversized (over 1536 bytes) or unavailable QR rendering falls back to a private local reply file (maximum 8192 bytes).

Remote Login must already be enabled and allow the selected account. Missing public host keys require separate informed consent before `sudo ssh-keygen -A` creates only missing keys. The iPad key grants only local TCP forwarding to `127.0.0.1:4500`, without shell, PTY or agent forwarding. Reverse TCP and Unix-socket forwarding are disabled for the entire selected account. Before granting the key the script validates SSH syntax and effective settings. To prove those settings also apply to the iPad's remote connection, it accepts the standard root-owned `100-macos.conf` Include of `/etc/ssh/crypto.conf` only when its trusted leaf contains Ciphers, KexAlgorithms and MACs. The crypto path may be a regular root-owned nonwritable file or Apple’s exact root-owned `crypto/apple.conf` symlink. The containing directories and final regular nonlink leaf must also be root-owned and nonwritable by other accounts. Link permissions are not treated as access controls; custom, chained, dangling, escaped or newline-suffixed targets stop for review. Other nested includes and conditional Match selectors other than exact selected User or all require review. An existing address/host/group policy requires manual review instead of a potentially unsafe grant.

A kernel-held `lockf` descriptor serializes setup mutation/display and releases after process death. Foreground children close that descriptor; the optional LaunchAgent uses a separate kernel-held instance lock that survives exec. Another iPad or an expired-code retry can reuse the verified server. The script never kills an unknown listener. Receipt writes synchronize file contents and parent directory metadata, then use macOS F_FULLFSYNC as a storage barrier. New-token contents are synchronized before provenance, and both rename directories are synchronized before the publication barrier. Key append and policy installation are synchronized before handoff-ready. A no-secret prepared token receipt is durable before atomic token publication. App Server exec is gated until its PID/start/token ownership receipt is durable. Reuse requires the exact PID/start identity, unchanged token inode/hash, pinned binary receipt and exclusive loopback listener. The user chooses background startup or the foreground Terminal alternative. Foreground exit stops only the exact owned child; background setup exits without stopping the verified LaunchAgent. Both preserve SSH grants and the persistent token.

`setup-receipts/<public-key-digest>.json` records the exact authorized key line, policy path/hash, planned ownership, shared token/server receipt paths, stage and revocation guidance. Its prepared stage precedes key/policy mutation; handoff-ready is recorded before private display. A failed setup rolls back only its exact newly added key, newly installed unchanged policy, exact new token and exact owned process. Restart failure restores the previous server receipt so the existing bearer remains reusable. A completed receipt without its token prevents silent rotation. Re-running the same key preserves the initial receipt and unrelated keys/configuration.

Dismissal is not an authenticated iPad completion acknowledgement: the key, token and server remain available. Revoke an iPad by removing only its receipt's exact `addedPublicKeyLine` from `~/.ssh/authorized_keys` (the advanced device revoke command does this). The account-wide policy may protect other clients, and token rotation affects every paired iPad; keep both until intentionally reviewed. A receipt contains no bearer/private key.

After an abrupt crash, the next acquired setup lease clears only declared private files (`private-reply.json`, `connection.png`, `new-token`) from sessions with a verified Screenpunk ownership marker. Public request/source/journal evidence in that old session is preserved for review; unknown paths are untouched. No background expiry service is installed. A powered-off or forcibly killed renderer cannot erase its display files until the next setup run or explicit owner cleanup; all such files remain account-private.

Setup v2 also handles an earlier stopped foreground setup with a saved bearer but no ownership receipts. Only after explicit local consent, it rechecks the exact private file identity/hash, listener absence and absence of conflicting provenance, then atomically publishes an exclusive `adopted-legacy-token` receipt. This records present approval to reuse an unchanged file, not a historical creation claim. The old token is never marked newly created, so cancellation/startup failure retains it; cleanup may stop only a new exact owned child. Running legacy servers without receipts remain behind a clear manual gate and are never stopped or adopted automatically.

The page presents the six actual setup stages in order, including the existing-connection **Connection details → Advanced → Pair again** path and the distinction between the downloaded `.sh` script and the iPad's `Screenpunk-setup-request.json`. Oversized selections stop before SSH authorization and explain that distinction.

Setup v3 embeds `macos/ssh-audit.sh` as the shared read-only metadata/content gate. The production script and read-only host verification execute the same function and embedded native code. It resolves only the specifically permitted one-hop Apple link and sends the checked physical leaf to the algorithm audit. The earlier v2 host verification ran the native content parser separately; reading through the link passed while the actual v2 shell regular-file gate rejected it. Regression fixtures now use the real Apple symlink layout by default, and exact extracted v2/v3 gates are checked against host metadata without executing setup or touching SSH/authentication state.

## Optional background startup (v4)

The Mac owner explicitly chooses **Enable background startup** in the native setup dialog. This installs the per-user label `xyz.screenpunk.local-agent` at `~/Library/LaunchAgents/xyz.screenpunk.local-agent.plist`; it is not a system daemon or a helper app. The plist is an owned regular 0600 file, with only paths and a fixed environment (`HOME`, dedicated `CODEX_HOME`, system `PATH`). Its arguments are `/bin/sh`, the private `setup-service/manage-v4.sh`, and `run`. The private controller/native sources and cached plist are owned and hashed in `setup-service/install.json`. The bearer stays in its existing singly linked 0600 file, never in plist arguments/environment, URLs or logs.

`RunAtLoad` and `KeepAlive` start it at GUI login and restart exits/crashes while the user stays logged in. Restart attempts are throttled to 30 seconds. The runner validates the exact Codex path/version/hash, token inode/hash/ownership and service files, publishes a durable new PID/start-identity receipt before exec, and keeps the same authenticated loopback address, feature restrictions and workspace. Every restarted instance refreshes that receipt without rotating the bearer. A private instance FD lock remains held across exec; a leftover lock file is reusable after the process exits.

The Mac must remain **signed in, awake and reachable**. Locking the screen is supported. Logout stops the user session's job; after reboot the user must sign in before iPad can connect. Sleep, closed lid, shutdown and network changes can interrupt reachability. Setup never changes power settings or enables Remote Login. **Terminal only** remains an explicit alternative requiring the setup Terminal to stay open.

For an existing v3 foreground setup, click **Done** on its old QR dialog first to release the setup-display lock, while keeping the old Terminal open. V4 separately asks before moving the exact verified PID/start instance to background startup; it discloses the brief disconnect and rechecks the unchanged token, receipt and loopback listener immediately before stopping that one instance. Unknown listeners and loaded job definitions are never stopped. Private files are staged first; the active LaunchAgent plist is published atomically without overwrite only after migration approval and a fresh label check. A cancelled migration leaves the old connection running and no new autoload plist.

If background startup fails after an approved stop, setup boots out only its exact newly owned job, removes only its exact new autoload plist, and restores the pinned foreground server using the unchanged credential. The Terminal then remains necessary. A later pairing failure after successful verified migration preserves the healthy new background server for the existing pair and rolls back only the new iPad grant. A failed restoration stops/reaps any newly created foreground child, preserves credentials and the receipt backup, and reports the need for review. Foreground restoration waits have exact PID/start signal cleanup; they do not leave a hidden process behind when that Terminal closes.

Management commands are explicit user-run actions:

```
/bin/sh "$HOME/.codex/screenpunk-local/setup-service/manage-v4.sh" status
/bin/sh "$HOME/.codex/screenpunk-local/setup-service/manage-v4.sh" start
/bin/sh "$HOME/.codex/screenpunk-local/setup-service/manage-v4.sh" restart
/bin/sh "$HOME/.codex/screenpunk-local/setup-service/manage-v4.sh" uninstall
```

`status` inspects the owned job. `start` loads the exact owned plist or starts its existing job. `restart` briefly disconnects clients by unloading/reloading only that verified job. `uninstall` unloads it and removes only unchanged owned service/controller/plist files; it retains a no-secret uninstall receipt, **SSH keys, token, Codex home, workspace and iPad pairing data**. Rerun public setup to enable it again. Existing or newly appeared unknown/tampered files/jobs stop for review. V5 parses the actual bounded `launchctl list label` diagnostic grammar and rejects unknown structures; the explicitly non-API `launchctl print` format is not parsed. The v4 controller bytes are retained for the helper-only repair; its legacy plist comment does not describe the corrected native parser.

Managed stdout/stderr are `/dev/null`, so no model request/reply/account payload is logged. A constant-size `setup-service/status.json` is atomically replaced with nonsecret startup stages (including pin failure), while launchd's job status and the app's connection diagnostics provide failure information. This deliberately trades raw server logs for privacy and bounded storage.

All lifecycle regression commands use a fake `launchctl`, fake Codex/SSH commands, private fake HOME/PATH and owned synthetic processes. They verify opt-in/install, exact job identity, restart/uninstall, persistent credentials, unknown-label/file rejection, cancellation, background failure fallback, post-ready pairing failure, late-plist publication races, restored-child TERM cleanup and instance-lock lifetime. No agent has installed, enabled, stopped or restarted an actual host service.


## Setup v5 native status parsing and verified v4 repair

macOS `launchctl list <label>` emits a diagnostic dictionary with semicolon-delimited array items, rather than a Foundation property list. V4 tried to decode it as a plist and dereferenced an unwrapped nil value as `job.Label`; its XML test shim missed that format. V5 uses a bounded strict parser for the actual diagnostic grammar, rejects duplicate keys and malformed identity fields, and verifies the exact label, program arguments and PID. Unsupported future formats stop for review. The native regression runs production JavaScript through `osascript`, with a specimen captured from macOS and optional read-only checks of a known existing job; full setup fixtures emit the same real grammar.

V5 retains the version4 service ABI and controller paths. When an installed helper matches the frozen v4 source and every ownership check passes, setup offers an explicit helper repair. It preserves the running process, controller, plist, SSH grants and saved credential. Durable original backups and a consent journal precede replacing only `native-v4.js` and its recorded checksum in `install.json`. A proven interrupted repair resumes; unknown or conflicting files stop for review. The agent does not run this repair on the user's Mac during project validation.

The v4 download remains immutable at SHA256 `311a4d48ccd6c84637521e9c6291c38813202f3fa869dadf5db7eb05f7557e5e`. A v4 failure after approved migration can leave its background job running with a prepared installation receipt. Inspect the exact job, PID/start identity, listener and ownership receipts before recovery; do not launch a second server or blindly unload the job.


## Setup v6: re-enable after uninstall

V6 fixes the public setup rerun after a deliberate background uninstall. The retained `install.json` records `uninstalled`, while uninstall has removed its controller, native helper and cached plist. V5 incorrectly tried the helper-upgrade inspection before the normal installer could restore those missing owned paths. Both a fresh v5 installation and an installation previously repaired from v4 could stop there.

When that retained state is present, setup asks again whether to use background startup or Terminal only. Terminal only leaves background startup uninstalled. For background startup, v6 first checks the private uninstall manifest, unchanged token inode/hash, current reviewed native/controller/plist source hashes, and exact ownership/content of any service file or LaunchAgent plist still present. Any loaded job at the label stops recovery for review. Only then does a separate **Re-enable** consent dialog authorize the normal installer to refill missing owned files and start the service. Cancellation leaves its uninstall receipt, credential and missing service files unchanged; unknown files are never overwritten. Existing native-helper repair journals and original backups remain unchanged.

The same gate handles a legitimate interrupted v5 install whose `prepared` manifest is durable but some owned service files are still missing. Every present file must match the reviewed sources; a separate **Resume** consent precedes filling missing files. A complete prepared v4 installation continues through the existing journaled helper-repair path.

This is a setup-shell correction. The v5 native helper bytes, v4 controller ABI/paths and native receipt format remain unchanged, so the existing helper hash and its recorded repair history remain verifiable. The public v5 download remains immutable at SHA256 `a54dc9fc1daedd4f95b8e2be126629c0dc83bdd63eb8bbc6076fb88734102fe3`. V6 has a new URL and checksum. All re-enable tests use isolated fake homes and a fake LaunchAgent implementation; project validation does not install or operate a host service.
